# CursorFlow 技术架构设计

> 关联 PRD：[CursorFlowPRD.md](../CursorFlowPRD.md)
> 本文是整套技术文档的总纲，定义系统分层、模块边界、线程模型与数据流。各模块详细设计见 02–05 号文档。

## 1. 架构总览

系统采用四层架构，自上而下单向依赖，禁止跨层调用：

```
┌─────────────────────────────────────────────┐
│              QML UI Layer                    │
│  Dashboard / Charts / Settings / TrayMenu    │
├─────────────────────────────────────────────┤
│           C++ Controller Layer               │
│  StatsController / DataManager / Settings    │
├─────────────────────────────────────────────┤
│           InputCapture Thread                │
│  PlatformHook(Win/Mac/Linux) → CounterBuffer │
├─────────────────────────────────────────────┤
│            Storage Layer                     │
│  Database (SQLite via Qt SQL)                │
└─────────────────────────────────────────────┘
```

| 层 | 职责 | 关键类 |
|----|------|--------|
| QML UI | 数据展示、图表渲染、交互 | `DashboardPage`、`ChartsPanel`、`SettingsPage` |
| Controller | 聚合采集增量、暴露 QML 可绑定属性、执行读写 | `StatsController`、`DataManager`、`AppSettings` |
| InputCapture | 平台钩子采集原始事件、距离计算、异常过滤 | `InputCaptureWorker`、`platform/WinHook` 等 |
| Storage | SQLite 建表、写入、清理、查询 | `Database`（单例封装 QSqlDatabase） |

依赖方向约束：

- UI 层只依赖 Controller 层暴露的 QML 单例/上下文属性；
- Controller 层通过信号槽与 InputCapture 通信，不直接操作平台 API；
- InputCapture 与 Storage 不直接互通，写入由 Controller 定时驱动。

## 2. 线程模型

```
主线程 (GUI)                采集线程 (QThread)
┌──────────────┐           ┌────────────────────┐
│ QML 渲染/交互 │           │ InputCaptureWorker  │
│ DataManager  │◀── 3s增量 ──│ 钩子回调 → 原子计数  │
│ 定时写库(1h)  │           │ 欧氏距离累加         │
└──────────────┘           └────────────────────┘
```

- **采集线程**：独立 `QThread`，宿主平台钩子。事件回调内只做轻量计算（坐标差累加、计数器自增），使用 `std::atomic` 计数器，无锁。
- **增量提交**：`QTimer` 每 3 秒在采集线程触发一次 flush，将增量通过队列信号交给主线程的 `DataManager`（跨线程信号槽自动排队连接）。
- **定时写库**：`DataManager` 内 `QTimer` 每小时将聚合数据写入 SQLite；同时接收退出前 flush。
- **UI 刷新**：`StatsController` 属性变更通过 `NOTIFY` 信号驱动 QML 绑定更新，刷新节流至 ≥1 秒一次，避免频繁重绘。

线程间共享数据仅通过以下三种方式：atomic 增量缓冲区、排队信号槽、SQLite（单连接仅主线程使用）。

## 4. 关键数据流

### 4.1 采集 → 展示（实时）
```
系统事件 → 平台钩子回调 → InputCaptureWorker 增量缓冲
  → 3s flush → (信号) → DataManager 合并到当日缓存
  → StatsController 属性更新 → QML 自动重绑定刷新
```

### 4.2 展示 → 持久化（小时级）
```
DataManager 小时定时器到期
  → UPSERT daily_stats / hourly_stats 当日当小时行
  → 写入成功后发出 statsSaved 信号（供托盘摘要、导出刷新）
```

### 4.3 查询 → 图表（历史趋势）
```
QML HistoryPage 请求 7/30 天数据
  → StatsController.queryRange() → DataManager SELECT
  → 返回 QVariantList → TrendChart 数据源更新 → Canvas 重绘
```

## 5. 平台抽象设计

`IPlatformHook` 统一三平台差异：

```cpp
class IPlatformHook {
public:
    virtual ~IPlatformHook() = default;
    virtual bool start(Callback cb) = 0;   // cb(event) 由钩子线程调用
    virtual void stop() = 0;
    virtual bool isAccessibilityGranted() const { return true; } // macOS 专用
};
```

| 平台 | 钩子 API | 线程要求 | 已知限制 |
|------|----------|----------|----------|
| Windows | `SetWindowsHookEx`（低级鼠标/键盘钩子） | 安装线程必须有消息循环 | 杀软可能误报，需代码签名 |
| macOS | `CGEventTap`（listenOnly） | 需辅助功能权限 | 首次启动需引导授权（PRD 风险项） |
| Linux | XInput2 (X11) | 需要 X 连接 | Wayland 下能力受限，MVP 不支持 |

平台选择在 `main.cpp` 编译期通过宏完成（`#ifdef Q_OS_WIN` 等），运行时仅暴露 `IPlatformHook` 接口。

## 6. 错误处理与降级策略

| 场景 | 策略 |
|------|------|
| 钩子安装失败（权限/杀软） | 弹窗提示 + 托盘图标变灰，UI 显示"未在采集"状态 |
| macOS 未授权 | 启动时检测并弹出引导页，跳转系统设置 |
| SQLite 写入失败 | 重试 3 次，仍失败则将数据保留在内存队列，界面显示离线徽标 |
| 数据库损坏 | 检测到 SQLITE_CORRUPT 时备份原文件后重建 |
| 单实例重复启动 | QLocalServer 锁，二次启动仅唤起已有窗口 |

## 7. 性能预算（对应 PRD 非功能需求）

| 指标 | 目标 | 实现手段 |
|------|------|----------|
| 空闲 CPU < 1% | 采集回调仅原子操作；flush 3s 一次 | 无轮询、无忙等 |
| 内存 < 50 MB | 图表仅缓存 30 天数据；粒子动画可关闭 | PRD 3.2 可选开关 |
| 窗口打开 < 500 ms | 主窗口启动即加载，图表延迟加载数据 | 懒加载 HistoryPage |
| 图表渲染 < 200 ms | Canvas 自绘而非 Qt Charts 大粒度 Item | 见 04 号文档 |
| 安装包 < 15 MB | 静态编译 Qt 核心（裁剪模块） | 见 05 号文档 |
